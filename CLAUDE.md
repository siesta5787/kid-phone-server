# Kid Phone Server — Project Context for Claude Code

## What this is

A lightweight, purpose-built parental-control server for the Kid Phone project. It's the sole backend for the client - there is no other MDM server or protocol involved. An earlier prototype used a different MDM stack entirely; that's been fully replaced, not extended, and none of its code, protocol, or data model carried over.

The client is a separate repo: `kids-launcher-mdm` (a custom Kotlin Android launcher that's also the Device-Owner MDM agent, package `com.kidslauncher.mdm`, networking code in `server/`). It speaks this server's API directly - enrollment, policy fetch, and status reporting are all this repo's own device-facing routes under `/api/devices/*`. See that repo's own `CLAUDE.md` for client-side architecture.

**Both repos are public** (as of 2026-07-31): `siesta5787/kid-phone-server` (GPLv3) and `siesta5787/kids-launcher-mdm` (GPLv3 for its own code; the inherited app-list screen stays MIT per `LICENSE-MIT-UPSTREAM` in that repo - it's a fork of Josia Pietsch's µLauncher, though the fork no longer describes itself that way since almost everything else - the gesture system, Minimalist Mode, the whole parental-control layer - is original).

## Tech stack

Deliberately mirrors `board-game-tracker` (another self-hosted Pi app by the same developer) since it already solved the boring-but-essential infrastructure for this exact hardware target:

- **Language:** Rust, **Web framework:** Axum, **Database:** SQLite via `sqlx` (WAL mode)
- **Templating:** Askama (compile-time-checked server-rendered HTML, no JS build step, no frontend framework) - templates are compiled into the binary, so editing one requires a rebuild, not just a file save. A plain `cargo run` dev server (no `cargo watch`) needs to be manually killed and restarted after any template/static change.
- **Sessions/auth:** `tower-sessions` + `tower-sessions-sqlx-store`, `argon2` for the admin password, mandatory TOTP 2FA
- **UI:** mobile-first bottom tab bar (Dashboard / Devices / Apps / DNS/Filters / Settings, see `templates/partials/app_header.html`), installable PWA (`static/manifest.webmanifest`, minimal install-only service worker at `templates/sw.js` - no offline page caching, deliberately, since this app handles session cookies and device bearer tokens), light/dark theming via `prefers-color-scheme` CSS variables (no manual toggle)
- **Hosting target:** Raspberry Pi Zero 2 W (or similar aarch64 board), `aarch64-unknown-linux-musl` cross-compiled via GitHub Actions on every `v*` tag (`.github/workflows/release.yml`, uses `cross`) - `deploy/install.sh` downloads the latest release and sets up a systemd service

## Architecture

- **Two completely separate auth systems**: admin sessions (`tower-sessions`, cookie-based, for the parent-facing web UI) and device bearer tokens (`Authorization: Bearer <token>`, for the phone's API calls). A device is never a session; an admin never touches the device API.
- **Enrollment is a one-shot code, not a device-number+URL pair.** The admin generates a short human-typeable code from a device's page; the phone POSTs it once to `/api/devices/enroll` and gets back a bearer token in return. The code is cleared from the DB the moment it's used - it can never be replayed.
- **`kiosk_desired` is server-authoritative** - the admin UI sets it, the device applies it automatically on its next sync, no on-device confirmation or local override switch. Fully built and confirmed working live on the physical test phone, using the full `lock_task_features` bitmask - status bar info, home, recents, and keyguard are always forced on (not admin-configurable; see the gotcha below for why keyguard specifically can't be optional), leaving only notifications and the power button menu as real per-device choices.
- **Friendlier allowlist**: the device reports its installed apps (`{package_name, label}` pairs) in every status heartbeat; the admin UI renders checkboxes from that real, current list rather than asking a parent to hand-type Android package names. See `device_status.installed_apps_json` and `handlers::devices::view_device`.
- **Schedule fields are minutes-since-midnight** (`weekday_start_minutes` etc.), matching the client's `KidModeEnforcer.kt` decision logic (including overnight-wraparound for bedtime windows crossing midnight) - the server just stores/serves this data. The admin UI converts to/from HTML `<input type="time">` values at the handler boundary (`devices::minutes_to_time_input`/`time_input_to_minutes`); an empty string round-trips to `NULL`/no-restriction correctly (there are explicit "Clear schedule" buttons in `device_detail.html` since native time inputs don't reliably expose a way to blank themselves).
- **WiFi/Bluetooth restrictions**: `wifi_mode`/`bluetooth_mode` per device, `"open" | "restricted" | "disabled"`. WiFi only supports open/restricted (the "disabled" mode was removed client-side - unreliable in testing, no strong use case). Bluetooth keeps all three, confirmed working.
- **Offline override PIN**: a per-device PIN (PBKDF2-HMAC-SHA256, `security::hash_pin`/`verify_pin`), cached hashed on the device so it verifies with zero network. Entering it correctly on the phone lifts every restriction for a bounded window and self-heals the moment the device can reach the server again. The client's Settings screen is also gated behind this same PIN, plus a separate manually-toggled "pause all restrictions" kill-switch that does *not* auto-clear (unlike the PIN override) - an emergency escape hatch if a policy or client update ever ships something broken.
- **Apps tab is a unified list+detail structure** (`/apps` → `/apps/tracked/{id}`) covering every app the server pushes to devices, including the launcher's own self-update - it's just another `tracked_apps` row (GitHub-sourced, `include_prereleases` on, since its CI only ever publishes to a rolling `pre-release` tag). The old launcher-specific `launcher_releases` table/routes/handlers (`handlers::releases`) are fully retired, not just deprecated - there is exactly one app-update system now, not two.
- **`tracked_apps.source_type`** is `"github"` (poll a repo's Releases hourly, or on-demand via "Check now") or `"manual"` (admin uploads an APK + types a release label directly, via `/apps/tracked/{id}/upload` - no polling, no repo). Both feed the exact same `latest_release_tag`/`latest_release_file_path` columns and the exact same device-facing API (`handlers::device_api::tracked_app_updates`), so nothing downstream needs to know or care which source produced a given cached release.
- **A GitHub-tracked app's release identity is compared as `(tag_name, asset_id)`, not tag alone** - `fetch_latest_release` hits the Releases *list* endpoint (`/repos/{repo}/releases`), not `/releases/latest` (which only ever returns non-prerelease, non-draft releases - would never find anything for a repo, like this project's own kids-launcher-mdm, that only publishes to a rolling prerelease tag; same problem Obtainium solves the same way). A rolling tag's `tag_name` never changes between pushes, but GitHub gives the replaced asset a new numeric `id` every time, so `latest_release_asset_id` is what actually detects a new build for those repos. The composite `"{tag}@{asset_id}"` string is what's sent to devices as `release_tag` (see `device_api::tracked_app_updates`) - the client's own "is this different from what I last installed" check is plain string equality, so it needs the asset id folded in to work correctly for rolling tags.
- **`/devices/provision`** (`handlers::provisioning`) generates a QR code for Android's standard 6-tap zero-touch Device Owner provisioning flow, as an adb-free alternative to the existing enrollment-code system - not per-device, not persisted, just a form that renders a QR code from a mostly-constant payload (admin component + signature checksum barely ever change; the download URL is `kids-launcher-mdm`'s rolling `pre-release` GitHub Release tag, so the QR stays valid across every new build). Does **not** work on GrapheneOS - its setup wizard has no `ManagedProvisioning` trigger built in at all yet (confirmed by searching its source directly; tracked at github.com/GrapheneOS/platform_packages_apps_SetupWizard2/pull/40, open/unmerged) - works on stock Android and most custom ROMs today. The signature checksum (`SIGNATURE_CHECKSUM` constant) is the signing certificate's SHA-256 digest, base64url-encoded with no padding - **not** the same as the whole-APK checksum (different source data, different Android extra key); recompute via `apksigner verify --print-certs` (gives the digest as hex) if the signing key is ever rotated. After provisioning, the device still goes through the normal per-device enrollment-code flow in Settings, same as an adb-provisioned device - this only replaces the "get the app installed and made device owner" step.
- **DNS/Filters (`/dns`, `src/dns_engine.rs`, `handlers::dns_filter`) is a Pi-hole-style DNS content filter built directly into this binary**, on `hickory-server`/`hickory-resolver` (MIT/Apache-2.0) - not on any AGPL codebase (crab-hole was researched as a design reference only, never depended on or copied from; see the module doc comment on `dns_engine.rs` for the full reasoning). Global/singleton, not per-device: a device is scoped to this filtering purely by choosing this Pi as its Tailscale exit node (a separate, OS-level decision) plus the `iptables` redirect below - nothing in the DNS engine itself is device-aware. Blocking is `hickory_server::store::blocklist::BlocklistZoneHandler` (a ready-made part of the library itself, not custom code) chained ahead of `store::forwarder::ForwardZoneHandler` in a `Catalog` for the root zone; `Catalog` itself implements hickory's `RequestHandler` and does the "check blocklist, else forward upstream" chaining natively (`LookupControlFlow::Break` on a hit) - our own `Handler` just wraps it to track query/blocked-query stats. Settings/blocklist/custom-domain changes call `dns_engine::rebuild`, which reconstructs the whole `Catalog` from the DB and hot-swaps it into a shared `Arc<RwLock<..>>` - no process restart, no DNS blip, ever. The **only** privileged part of this feature is the `iptables` PREROUTING DNAT rule (port 53 on the `tailscale0` interface → this engine's own unprivileged port 5300), requested through the exact same flag-file/root-owned-watcher mechanism `system_maintenance.rs` already uses for reboot/Tailscale-update/etc (`action_dns_filter_enable`/`disable` in `deploy/install.sh`'s `actions.sh`).
- **Find My Device (`/devices/locate`, `handlers::locate`) is locate/ring/lock/wipe for a lost or missing device**, referencing [fmd-foss/fmd-android](https://gitlab.com/fmd-foss/fmd-android) (GPLv3) for the feature set only - not its actual protocol, which doesn't fit this project (SMS/IM delivery, its own crypto/server stack). Built on the existing sync loop instead: `device_commands` is a small queue table (`ring`/`lock`/`wipe`/`locate`, the last currently unused - queuing UI only exists for the first three), and `PolicyResponse.pending_command` surfaces the oldest undelivered row for a device - `handlers::device_api::policy` marks it `delivered_at` the instant it's served, so a retry before the device acknowledges never hands out the same command twice (see `handlers::locate::queue_command`'s doc comment for the "your last action wins" replace-semantics on the admin side, including how it doubles as a way to cancel a queued-but-undelivered wipe). `device_locations` is a plain history table (not just a latest-point column set), attached to every regular `StatusReportRequest.location` from the device - not just after an explicit `locate` command - so the map's trail stays fresh on its own; pruned to 30 days by `run_location_pruning`. The admin map is vendored Leaflet (`static/leaflet/`, BSD-2-Clause, downloaded once from unpkg and committed - no CDN dependency, no build step) against public OpenStreetMap tiles, fed by a plain `/devices/{id}/locations.json` endpoint. Wipe is gated by typing the device's exact name to confirm, same pattern as backup restore/delete in `backups.html` - it's the only command that can never be acknowledged back, since the device is gone.

## Non-obvious gotchas hit so far

- **axum's built-in `Form` extractor cannot deserialize repeated same-named form fields** (e.g. multiple checked checkboxes named `allowed_packages`) into a `Vec<String>` - errors with `invalid type: string "...", expected a sequence`. Fixed in `handlers::devices::update_policy` by taking raw `axum::body::Bytes` and parsing manually with `form_urlencoded` instead of `Form<T>`. Reuse this pattern for any future repeated-checkbox-group field.
- **Browsers cache `/static/*` assets aggressively with no revalidation** - editing `style.css` and reloading can silently keep serving the old cached copy even after a hard navigate. `partials/head.html` links it with a `?v=N` cache-busting query param (bump `N` when the stylesheet changes) - the same pattern `board-game-tracker` already uses.
- **The dev server is a plain `cargo run`, not `cargo watch`** - it will not pick up template or static-file changes on its own. Kill the running `cargo`/`kid_phone_server` processes and restart after any such edit, or you'll be testing against stale HTML/CSS while genuinely-fresh files sit on disk (this has caused real confusion mid-session more than once).
- **`LOCK_TASK_FEATURE_KEYGUARD` is disabled by default in Android's lock-task mode, and that suppression is enforced at the `DevicePolicyManager`/`system_server` level - it keeps applying even before a device is decrypted (Before First Unlock), when the client app's own process can't run at all.** A real device got stuck at boot after GrapheneOS's auto-reboot-after-inactivity feature re-locked storage while this bit was off for that device: no keyguard to enter a PIN into (suppressed by policy) *and* no launcher available either (this app was the exclusive enforced Home app, and its components aren't resolvable pre-unlock) - a total deadlock, recoverable only via hardware-level recovery mode. Fixed by forcing `LOCK_FEATURE_KEYGUARD` on unconditionally in `update_policy`, same as the other always-on features - it's no longer admin-configurable. The tradeoff this accepts: every kiosk-mode device now also requires a PIN to resume from sleep, not just after a reboot, since Android doesn't expose those as separate bits.
- **`rustls` 0.23+ needs an explicit process-wide default `CryptoProvider` installed before *any* TLS connection works, and there's no error at the call site that says so.** Without `rustls::crypto::ring::default_provider().install_default()` early in `main()`, the DNS filter's DoT upstream forwarding just silently failed every query with `NetError(NoConnections)` - no panic, no obvious log line pointing at the real cause, only found by turning on `hickory_resolver=debug` tracing and noticing the connection attempt simply never got anywhere. Install exactly one provider once, at startup, before anything that might open a TLS connection runs.
- **A missing root-certificate-store feature is a second, separate way to get the exact same silent `NetError(NoConnections)` failure** as the gotcha above, even with the crypto provider correctly installed - `hickory-resolver` needs either its `webpki-roots` feature (bundled Mozilla root store, what this project uses - portable, doesn't depend on the OS having a usable cert store, which a minimal Pi image might not) or `rustls-platform-verifier`/`native-roots`, or TLS certificate validation has no trust anchors and every handshake fails post-connect with no distinguishing error. If DoT forwarding ever breaks again, check both of these before assuming it's a network/firewall issue - `Test-NetConnection`/`nc` succeeding against the upstream's port proves nothing here, since the TCP+TLS handshake itself can still complete while certificate validation silently fails afterward.
- **`tailscale status --json | grep '"ID"'` matches every device in the tailnet, not just the Pi itself** - the JSON always includes both `Self` and every `Peer`, each with their own `"ID"` field, regardless of the `--self` flag (which only affects the plain-text table output, not JSON structure). To get just the Pi's own stable node ID (the value `AppEnforcer.applyVpnRestrictions` on the client pushes to Tailscale as `ExitNodeID`, and what goes in `device_detail.html`'s "Exit node ID" field), use `tailscale status --json | jq -r '.Self.ID'`.
- **QR-code zero-touch provisioning (`handlers::provisioning`) failed live on a genuine GMS-certified device (Motorola Moto G Play 2024, Android 14) during the Device-Owner-provisioning step specifically** - not app installation (the identical APK installs fine as a plain sideload on that same device afterward, and the download URL/signature checksum were independently confirmed correct). Not yet confirmed via logs (no adb access reachable before `ManagedProvisioning` resets back to OOBE on failure), but the leading theory is that Google restricts the zero-touch/QR Device-Owner flow specifically to Play-Store-sourced DPCs on GMS-certified hardware - separate from whatever (if anything) gates a plain sideload install. If true, a release-signed (non-debug) build wouldn't fix this specific failure, since it isn't a signing/trust issue. This is in addition to the already-documented GrapheneOS limitation above (no `ManagedProvisioning` trigger at all) - so as of this writing, QR provisioning has no confirmed-working real-device target; manual `adb shell dpm set-device-owner ...` remains the reliable path everywhere.

## Data model (SQLite, see `migrations/`)

- `admin_users` - parent login accounts, TOTP secret, forced-password-change flag
- `devices` - one row per kid's phone: name, enrollment code (+ expiry, cleared on use), hashed bearer token, enrolled/last-seen timestamps
- `device_policy` - one row per device: allowlist JSON, schedule windows, `kiosk_desired`, `lock_task_features` (bitmask), `wifi_mode`/`bluetooth_mode`, `override_pin_hash`/`override_pin_salt`
- `device_status` - append-only heartbeat log: lock reason, kiosk-engaged, installed-app snapshot, app version, timestamp, `offline_override_used`
- `security_events` / `banned_ips` - admin login audit trail and lockout tracking
- `tracked_apps` - one row per app the server pushes to devices (including the launcher itself), GitHub-sourced or manually-uploaded - see the "Apps tab" gotcha above
- `dns_filter_settings` (singleton), `dns_blocklists`, `dns_custom_domains` - the DNS/Filters feature's config; global, not per-device, see the DNS/Filters gotcha above
- `device_locations` - append-only location history per device (30-day pruned), `device_commands` - the Find My Device remote-command queue (`requested_at`/`delivered_at`/`acknowledged_at`/`result`), see the Find My Device architecture bullet above

## Device-facing API (plain JSON, no envelope)

- `POST /api/devices/enroll` - `{enrollment_code}` → `{device_id, device_token}`
- `GET /api/devices/policy` (bearer) → allowlist, schedule, `kiosk_desired`, `lock_task_features`, `wifi_mode`, `bluetooth_mode`, `override_pin_hash`/`override_pin_salt`, `pending_command`
- `POST /api/devices/command-result` (bearer) - `{command_id, success, message}` → 204, never sent for a `wipe` command
- `POST /api/devices/status` (bearer) - `{lock_reason, kiosk_engaged, installed_apps, app_version, app_version_code, offline_override_used, location}` → 204
- `GET /api/devices/apps` / `GET /api/devices/apps/{id}/download` (bearer) - update check/download for every tracked app, including the launcher's own self-update
